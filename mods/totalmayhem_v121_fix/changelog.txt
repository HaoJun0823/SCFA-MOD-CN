2026-08-25  v1.1  禁用 8 个停机坪单位建造
  - 目标：4 阵营 × 2 型 = 8 个大型/小型停机坪
      * Cybran  : BRMGRND1(大) / BRMGRND2(小)
      * UEF     : BRNGRND1(大) / BRNGRND2(小)
      * Aeon    : BROGRND1(大) / BROGRND2(小)
      * Seraphim: BRPGRND1(大) / BRPGRND2(小)
  - 机制：Merge bp 走 table.merged（递归并集）无法删除 Categories，故用 hook 在
          蓝图合并后(ModBlueprints 阶段)剥离 BUILDBY*/BUILDAI* 类目，使四阵营（玩家与 AI）均不可建造。
  - 重要坑：sim 侧 lua/system/Blueprints.lua 里**没有** BlueprintsMerge 这个全局函数，
          只有 ModBlueprints。若在该文件里引用 BlueprintsMerge，FA 严格全局访问会抛
          "access to nonexistent global variable 'BlueprintsMerge'"，导致整份 blueprints.lua
          加载失败 -> categories 全局表建不起来 -> 后续 AI 文件 import 全崩(categories.MOBILE/FACTORY nil)。
          故本 patch 用标准 ModBlueprints 链式包装(与 BlackOps 系同 chunk)，绝不可引用 BlueprintsMerge。
  - Hook 方案（单点，非两个）：
      * 仅 hook/lua/system/blueprints.lua —— 链式包装 ModBlueprints，合并阶段剥离 8 单位类目。
        说明：LoadBlueprints() 在 sim 与 UI 两侧都会调用 ModBlueprints，故这一处 hook 同时覆盖
        玩家菜单与 AI；无需、也不应有额外的 UI 侧 hook。
      * 已删除原 hook/lua/ui/game/gamemain.lua：它顶层引用 OnGameStart，而该全局在 gamemain.lua
        加载时尚未定义，FA 严格全局访问直接抛 "access to nonexistent global variable 'OnGameStart'"
        导致 UI 侧崩溃。且该 hook 与 ModBlueprints 作用重复，删除后更干净、更稳。
  - 又一坑：不要在 hook 文件顶层引用"加载时尚未存在的全局"（BlueprintsMerge、OnGameStart 等），
      FA 的 Lua 会当作错误抛出并中断整个 chunk 加载；要用链式包装（先捕获已存在的函数再 function 覆盖）。
  - 验证：lupa 纯 Lua 仿真，8 单位 BUILDBY*/BUILDAI* 被剥离、其余类目保留、非停机坪单位不受影响；
      mod 内已无 .lua 引用 OnGameStart / BlueprintsMerge。

2026-08-25  v1.1.2  修复"ModBlueprints 进了、8 个都 HIT、但 BUILDBY* 没被删"
  - 根因（最隐蔽的一层）：剥离判定写的是 string.find(v, '^BUILDBY') / string.find(v, '^BUILDAI')，
          依赖 Lua pattern 的 '^' 起始锚点。但**本版 FA 的定制 Lua 5.0 里 string.find 是纯字面匹配、
          不支持 ^/$/% 这类 pattern**（已用 LOG 实锤：string.find(desc,'Ground Tarmac') 返回 23 字面子串
          匹配成功；而 string.find(v,'^BUILDBY') 把 '^BUILDBY' 当字面串去找 => 永远 nil =>
          not(nil)=true => BUILDBY* 被"保留" => 剥离形同虚设，日志里 after 与 before 完全一样）。
          这也是之前几次"本地 lupa 仿真通过、游戏里却不生效"的元凶：lupa 用 LuaJIT(标准 Lua 语义)，
          '^' 锚点能匹配；真实 FA 不能。两套环境 string.find 行为不一致，仿真不可尽信。
  - 修复：彻底不用 string.find 的 pattern，改用 string.sub(v,1,7) 取前缀做字面相等比较
          （'BUILDBY' / 'BUILDAI' 均恰为 7 字符），该写法在任意 Lua 实现下行为一致。
  - 验证：lupa 用用户 LOG 中的真实类目数组跑，brpgrnd1 after 已不含任何 BUILDBY*；
          nottarmac（非停机坪）类目完好保留 BUILDBYTIER1ENGINEER，确认无"误伤"。

2026-08-25  v1.1.3  修复"换 string.sub 后仍是 removed=0"

  - 验证：用户 LOG 中 brpgrnd1 的真实类目数组，纯表查找 (Python dict) 复刻 => removed=4，
          after 干净剔除全部 BUILDBY*、无误伤、无残留。该结果对 FA 同样确定成立。
  - 一并修正记忆：本项目 FA Lua 的 string.find / string.sub **均不可用于精确前缀/子串判定**，
          需要做这类匹配时一律改用「精确字符串集合 / 表键查找」或手动逐字符比对。

2026-08-25  v1.1.5  最终修复：根因坐实 + 双保险（手动重建 + UI 兜底）
  - ★ 根因彻底坐实（lupa 复现 + 真机 LOG 交叉验证）：
      * base utils.lua 的 table.removeByValue 实现是 `for k,v in pairs(t) do if v==val then table.remove(t,k) end end`。
        **两个问题**：① 无 return → 任何 `if table.removeByValue(...)` 计数恒 0（此前 removed=0 一半是假计数器）；
        ② pairs+table.remove 边遍历边删，在**标准 Lua** 下能删（lupa 复现 16→12 全删成功），但在 **FA 定制 Lua 真机**
        对「连续多条待删项」（停机坪的 BUILDBYTIER1/2/3ENGINEER, BUILDBYCOMMANDER 下标 3~6 连续）**静默失效**
        （真机 LOG: after==before）。→ 与 string.find/string.sub 同理：**FA 定制 Lua 的表遍历+原地删除组合也不可信**。
  - 最终方案（本版生效）：
      * 主修复 hook/lua/system/Blueprints.lua：**手动重建数组**——pairs 遍历一次、把要保留的类目塞进新表、
        整体 `bp.Categories = newcats` 赋值。纯表语义、不做原地删除，与 Lua 实现无关，一定生效。
        全部循环改用标准 `pairs()`（不依赖 FA 的 `for k,v in t` 扩展语法）。
      * 新增 UI 兜底 hook/lua/ui/game/construction.lua：包装全局 OnSelection，调用原版后把 sortedOptions.t1..t4
        中的 8 个 uid 剔除，有变化则按 base 标准路径 FormatData + choices:Refresh 重绘；整段 pcall 保护，异常静默。
        即使位掩码那条路因未预见行为失效，玩家建造菜单也绝不显示这 8 个单位。
